# Учёт рабочего времени

Небольшое веб-приложение: добавление сотрудников, таймер с описанием задачи, отчёт по записям и общему времени за период. Данные хранятся в SQLite и сохраняются после перезапуска.

**Стек:** Python 3.11+, FastAPI, SQLite (стандартная библиотека), один HTML-файл без сборки. Авторизации нет, данные вымышленные.

## Запуск

```bash
python -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate
pip install -r requirements.txt
uvicorn app:app --reload
```

Откройте http://127.0.0.1:8000. База создаётся в файле `timetracker.db` рядом с `app.py` (другой путь: переменная `TT_DB`).

## Тесты

```bash
pytest -q
```

Покрыты основные сценарии: добавление и дубликаты сотрудников, старт и стоп, **повторный запуск таймера** (409), стоп без старта, пустое описание задачи, **пустой отчёт**, фильтр по периоду, неверные даты, сохранение данных после «перезапуска» (новое приложение на том же файле БД).

## API

| Метод | Адрес | Что делает |
|---|---|---|
| POST | `/api/employees` | добавить сотрудника `{name}` |
| GET | `/api/employees` | список (с текущей задачей, если таймер идёт) |
| POST | `/api/timer/start` | `{employee_id, task}`; 409, если таймер уже идёт |
| POST | `/api/timer/stop` | `{employee_id}`; 409, если таймер не запущен |
| GET | `/api/report` | `employee_id`, `date_from`, `date_to` (ГГГГ-ММ-ДД) → записи и общее время |

## Решения

- Правило «у сотрудника один запущенный таймер» держится на уровне базы (частичный уникальный индекс), а не только проверкой в коде: два одновременных запроса не создадут две записи.
- Незавершённая запись в отчёте считается «до текущего момента» и помечается «(идёт)».
- Период в отчёте включает обе границы и считается по дате начала записи.

## Известные ограничения

- Даты и фильтр периода считаются по UTC, часовой пояс пользователя не учитывается.
- Уникальность имён чувствительна к регистру: «Анна» и «анна» считаются разными.
- Нет редактирования и удаления записей и сотрудников: по условиям задания это не требовалось.

## Что я проверил в сгенерированном коде

- Прогнал приложение вручную в браузере и нашёл недоработку: время начала записи показывалось в UTC (03:47 вместо местных 08:47), что сбивает с толку. Исправил: в таблице теперь местное время браузера. Фильтр периода по-прежнему считается по датам UTC (см. ограничения).
- Проверил, что повторный старт, стоп без старта, пустая задача и пустой отчёт возвращают понятные сообщения, а не падают.
- Запустил сервер, добавил запись, перезапустил сервер, и данные сохранились.
- Прочитал код, сгенерированный моделью: SQL написан с параметрами (без подстановки строк), вывод в таблицу идёт через `textContent`, а не `innerHTML`, поэтому HTML в названии задачи не выполнится.
